# Batamart — Flutter Client

Android client for Batamart. See `CLAUDE.md` and `docs/` for the full spec — this file only records
the architecture decisions made in Phase 1 so later phases don't re-derive them.

## Stack

- **HTTP**: `dio`, single instance in [lib/core/api/api_client.dart](lib/core/api/api_client.dart).
  An interceptor attaches `Authorization: Bearer <token>` from secure storage on every request; errors
  are normalized to `ApiException` using the backend's `{ error: string }` shape
  (`BACKEND_REFERENCE.md` §1.2).
- **State management**: `flutter_riverpod` (2.x, no code generation — providers are hand-written).
- **Routing**: `go_router`, table + auth/role redirect guards in
  [lib/core/router/app_router.dart](lib/core/router/app_router.dart) (built out in Phase 3).
- **Token storage**: `flutter_secure_storage`, wrapped in
  [lib/core/storage/token_storage.dart](lib/core/storage/token_storage.dart).
- **Local persistence** (cart — there is no cart API): `hive` / `hive_flutter`, initialized in `main()`.
  Boxes get defined in Phase 5 when the cart feature is built.
- **Environment config**: build-time `--dart-define=API_BASE_URL=...`/`APP_ORIGIN=...`, read in
  [lib/core/config/env.dart](lib/core/config/env.dart). **Updated in Phase 12 setup**: defaults now point
  at the real deployed backend, `https://www.batamart.com` (confirmed live — `GET /api/universities`
  already returns the real UNIZIK data). Note the `www`: the bare `https://batamart.com` 308-redirects
  there, which would silently mishandle POST bodies and send the wrong `Origin` header if used instead.
  Override for local development against a `next dev` server on the same machine:
  ```
  flutter run --dart-define=API_BASE_URL=http://10.0.2.2:3000 --dart-define=APP_ORIGIN=http://localhost:3000
  ```

## Folder structure

```
lib/
  core/
    api/        # ApiClient, ApiException
    config/     # Env (dart-define reads)
    router/     # go_router table
    storage/    # TokenStorage (secure storage)
    theme/      # AppColors, AppTypography, AppSpacing/AppRadii, AppTheme (light ThemeData)
    widgets/    # Reusable component library (Phase 2) — see below
  features/
    <feature>/
      data/           # repositories (talk to ApiClient)
      presentation/   # screens + riverpod providers
```

Each phase adds its own `lib/features/<name>/` folder (auth, marketplace, cart, orders, seller, wallet,
disputes, rider, ...) as it's built — they aren't pre-created empty.

## Phase 3 status — Auth & Onboarding

- **Screens** (`lib/features/auth/presentation/`): Splash, Onboarding, Login, Signup (email → OTP →
  details, all in one flow), OTP Verification, Forgot Password, Reset Password, Profile Setup, Rider
  Login, Become a Seller. Landing shells at `lib/features/home/presentation/` (`BuyerSellerHomeShell`,
  `RiderHomeShell`) wire in the Phase 2 nav shells — Home/Deals tabs are real as of Phase 4; Cart/Orders
  and the rider tabs stay "coming soon" placeholders until Phases 5/6/10.
- **State**: `AuthController` (`lib/features/auth/state/`) is the single source of truth for
  auth/role state — bootstraps from stored token on app start (calling `me()`; expired/invalid token
  forces re-login), exposes login/signup/reset/becomeSeller/toggleSellerMode/logout. `AuthRepository`
  wraps every `/api/auth/*` + `/api/riders/{login,register}` call from BACKEND_REFERENCE.md §3.1/§5.9.
- **Router guards** (`lib/core/router/app_router.dart`): a single `redirect` callback gates every
  route off `AuthController`'s state — bootstrapping → splash; unauthenticated → onboarding/login/etc.;
  authenticated RIDER → rider shell only; authenticated BUYER/SELLER without a complete delivery
  profile (hostel+room+landmark) → Profile Setup first, then the home shell.
- **CSRF workaround (your call)**: since the backend fix hasn't landed, `AuthRepository` applies
  BACKEND_REFERENCE.md §1.3's option 3 — sends `Origin: Env.appOrigin` on the 5 affected calls
  (`login-with-password`, `send-otp`, `reset-password`, `riders/login`, `riders/register`).
  `Env.appOrigin` defaults to `http://localhost:3000` (always allowed server-side); override for a
  deployed backend with `--dart-define=APP_ORIGIN=https://your-deployed-domain`. This is a documented
  stopgap, not a real fix — it silently breaks if the backend's allowed-origin config changes. Remove
  the `headers: _originHeader` argument on those 5 calls once the backend fix actually lands.
- **Google Sign-In — wired for real (updated in Phase 12 setup)**: `google_sign_in` (v7, Credential
  Manager-based) added; `GoogleAuthService` (`features/auth/data/google_auth_service.dart`) wraps
  `initialize`/`authenticate` and returns the ID token. `AuthRepository.continueWithGoogle` now returns a
  `GoogleAuthOutcome` (`GoogleAuthSuccess` or `GoogleSignupRequired`) instead of assuming every response
  has a `token`/`user` — the `mode: 'signup'` branch on a brand-new account returns a `signupToken`
  instead, which `SignupScreen` now accepts via a `googleSignup` constructor param (routed through with
  `context.push(AppRoutes.signup, extra: outcome)`) to pre-fill email/name and skip straight past the
  email-OTP step. Two OAuth client IDs are involved: an **Android**-type client (registered with this
  app's package `com.batamart.batamart` + debug SHA-1 `C9:F1:1E:B2:C5:A9:E0:B0:39:90:48:6D:AE:E2:CE:D2:
  3D:C7:E1:E6`, never referenced in code — Play Services looks it up by package+signature) and a **Web
  application**-type client (`Env.googleServerClientId`, passed as `serverClientId` — its ID must match
  the backend's `GOOGLE_CLIENT_ID` for the audience check in `POST /api/auth/google`
  (BACKEND_REFERENCE.md §3.1) to pass; reused the same Web client ID the existing web app already uses).
  ⚠ Remember to add a **second** Android OAuth client (same project, same package, the **release**
  keystore's SHA-1) once that keystore exists — see the "Android signing keystore" step — otherwise
  Google Sign-In will 10-error silently in release builds while working fine in debug.
- **Biometric login**: deferred (your call) — not implemented this phase.
- **Mockup mismatch flagged**: the "Welcome Back" mockup labels its first field "Email or Phone", but
  `POST /api/auth/login-with-password` only accepts `{ email, password }` — there's no phone-based
  password-login route (BACKEND_REFERENCE.md §3.1). Labeled the field "Email" to match what the API
  actually does; flagging per CLAUDE.md's "trust the API over a stale assumption" rule rather than
  building a phone-login path that doesn't exist.
- **No mockup provided yet** for Signup, OTP Verification, Forgot/Reset Password, Profile Setup, Rider
  Login, or Become a Seller (`docs/mockups/README.md`'s inventory only covers Login/Welcome-Back from
  the shared/onboarding set). Built these using the Phase 2 design system for visual consistency —
  provisional pending real mockups. Send those images whenever you have them and I'll restyle to match
  exactly; the navigation/behavior won't change.

## Phase 4 status — Marketplace & Product Browsing

- **Screens** (`lib/features/marketplace/presentation/`): Marketplace Home and Deals (both tab bodies
  in `BuyerSellerHomeShell`, matching the collage), Search, Most Bought, Product Detail, Product
  Reviews, Seller Directory, Seller Profile, Seller's Full Catalog. `ProductsRepository` wraps
  `GET /api/products/feed`, `GET /api/products` (search/filter), `GET /api/products/{id}`,
  `POST /api/products/{id}/view`, `GET /api/products/{id}/related`,
  `GET /api/products/people-like-you`, `GET /api/search/suggestions`,
  `GET /api/reviews/product`, `GET /api/sellers/{id}/reviews` (BACKEND_REFERENCE.md §3.3/§3.8).
- **Guest browsing is more limited than WEB_PAGES_REFERENCE.md implies (real API constraint, not a
  choice)**: `GET /api/products` and `GET /api/products/feed` both require a Bearer token +
  `user.universityId` server-side. Only `GET /api/products/{id}` and `GET /api/reviews/product` are
  actually public. So Marketplace Home/Deals/Search/Most Bought/Seller Directory/Catalog all require
  login here — only Product Detail and its Reviews screen work for a logged-out visitor (e.g. via a
  shared link), gated in the router's `_guestBrowsableRoutes` set. Add to Cart/Buy Now/Report still
  prompt login first either way, per the phase's own scope.
- **"Girlfriend's Day" banner is a placeholder** (`_CampaignBanner` in `marketplace_home_screen.dart`)
  — styled with the design system's campaign-pink token, not the real image/copy. Swap it for your
  actual banner asset whenever you send it; everything else on the screen is unaffected.
- **Seller Directory has no backing endpoint** — there's no `GET /api/sellers` list route anywhere in
  BACKEND_REFERENCE.md, only per-product `seller` sub-objects and `/api/sellers/{id}/reviews`.
  `sellerDirectoryProvider` derives a directory client-side from sellers seen in the already-loaded
  feed, so a seller with no product currently in the feed simply won't appear. Also, no inbound link to
  this page is documented anywhere in WEB_PAGES_REFERENCE.md's nav table, so I added a "Sellers" entry
  to the Profile tab placeholder as a reasonable, undocumented entry point — flagging in case you'd
  rather place it elsewhere.
- **Seller Profile is missing bio/join-date** — WEB_PAGES_REFERENCE.md describes this page as showing
  "rating, bio, join date, product grid, reviews," but no documented endpoint returns a seller's bio or
  join date, only `id, name, avgRating, trustLevel, completedOrders[, profilePhoto]`. Omitted rather
  than invented.
- **Category tabs on Deals** (All/Fashion/Electronics/Beauty, matching the mockup) send their label
  straight through as `GET /api/products`'s `category` param — there's no `/api/categories` endpoint to
  confirm exact key casing against, so verify these actually filter correctly once the API is reachable.
- **Most Bought** is a flat grid, not the web's day-grouped infinite scroll (no mockup was provided for
  this screen) — functional simplification, easy to extend once/if needed.
- **No mockup provided** for Search, Most Bought, Product Reviews, Seller Directory, Seller Profile, or
  Seller's Full Catalog — built consistent with the design system, same caveat as Phase 3's provisional
  screens.

## Phase 5 status — Cart & Checkout & Payments

- **Cart** (`lib/features/cart/`): client-local state only — there is no server-side cart API
  (BACKEND_REFERENCE.md §3.4) — persisted to a Hive box so it survives app restarts. Every add
  reconciles against `POST /api/cart/add` for a live price/stock/seller snapshot before merging into
  local state. Cart screen matches the mockup exactly: items grouped by seller, qty steppers capped at
  the server's `maxQuantity`, delivery-fee preview via `POST /api/delivery/quote`, "Secure Checkout".
- **Checkout** (`lib/features/checkout/`): matches the mockup — delivery address summary (+Edit),
  single order-notes field, escrow explainer card, order summary, "Pay with Flutterwave". The mockup's
  one combined notes field gets applied to every cart item's `orderNote` at pay time, since
  `payments/initialize`'s body shape is per-item (BACKEND_REFERENCE.md §3.5). Checks
  `GET /api/payment-availability` before allowing payment.
- **Payment flow decision**: used `webview_flutter` (the official Flutter-team package) to host
  Flutterwave's hosted-checkout page, rather than a third-party Flutterwave Flutter SDK — this was
  flagged as an open decision in BUILD_PLAN_12_PHASES.md Phase 5. Reasoning: the backend's whole flow is
  already redirect-based end to end (`initialize` → Flutterwave-hosted URL → redirects to
  `GET /api/payments/verify` → **another** redirect to `/orders?payment=success...` or
  `/checkout?error=...`, never JSON at any point per §3.5) — a generic WebView watching for those two
  URL shapes covers it fully, with no dependency on a third-party SDK's maintenance status. Order
  creation happens entirely server-side inside `payments/verify`; the app never sees the order until
  after the redirect chain completes, then clears the local cart on the detected success URL.
- **"Buy Now" adds to the shared cart then jumps to Checkout** — there's no separate express-checkout
  path in the backend, so an existing cart comes along for the ride. Documented in
  `product_detail_screen.dart`.
- **Two real bugs found and fixed in the Android manifest** (unrelated to Phase 5's own scope, but
  found while wiring the payment WebView's network calls):
  1. `android/app/src/main/AndroidManifest.xml` was missing `<uses-permission
     android:name="android.permission.INTERNET"/>` entirely. Debug builds happened to work anyway
     because Flutter's debug-only manifest separately declares it for hot-reload/VM-service
     communication — but a **release build** (`flutter build appbundle`, Phase 12) would have shipped
     with zero network access. Fixed by adding it to the main manifest.
  2. Android blocks cleartext (plain HTTP) traffic by default from API 28+, but `Env.apiBaseUrl`'s dev
     default (`http://10.0.2.2:3000`, for a local `next dev`) is cleartext — this would have failed on
     a real run with a cleartext-not-permitted error. Fixed with `android:usesCleartextTraffic="true"`
     in the **debug-only** manifest (`android/app/src/debug/AndroidManifest.xml`) — release stays
     cleartext-restricted since production must be HTTPS.

## Phase 6 status — Buyer Orders & Post-Purchase

- **Screens** (`lib/features/orders/`): Orders (status-tab list matching the mockup exactly), Order
  Detail (the universal screen from WEB_PAGES_REFERENCE.md — this is the buyer view only; seller/rider
  views reuse the same route in Phases 7/10), Review Product, Review Seller. `OrdersRepository` uses
  `GET /api/orders/my-orders` (not the legacy `GET /api/orders`) and `POST /api/orders/confirm-delivery`

  per BACKEND_REFERENCE.md §3.6's explicit warning).
- **"To Pay" tab will always be empty, by design**: the backend never creates an `Order` row until
  Flutterwave confirms payment (§3.5), so there's no reachable unpaid-order state in this app's real
  flow — the mockup's "To Pay" tab has nothing to filter for. Kept for visual parity, mapped to
  `PENDING` as the closest real status.
- **Live rider map is not implemented — needs a Google Maps API key you haven't provided yet.** Order
  Detail polls `GET /api/orders/{id}/live-location` every 15s (correctly matching the endpoint's
  polling-only design, no WebSocket/SSE exists) and displays the raw latest lat/lng + timestamp as text.
  Swapping in a real `google_maps_flutter` map view once you have a Maps SDK key is a contained change
  — the polling/data layer is already there.
- **`quantity` on `my-orders` is an assumption** — BACKEND_REFERENCE.md's documented response shape for
  `GET /api/orders/my-orders` doesn't list a `quantity` field (only the full `GET /api/orders/{id}` row
  does per the data model). Parsed defensively with a default of 1; verify the "N items" count on the
  Orders list against live data once reachable.
- **Order Tracking mockup folded into Order Detail**: the collage's separate "Order Tracking" frame is,
  per WEB_PAGES_REFERENCE.md, the same universal Order Detail screen while an order is in an active
  delivery status — not a separate route. Implemented as one screen that renders the stepper/rider
  card/live-location section conditionally on `order.status`.

- **Category is a free-text field, not a picker** — there's no `/api/categories` endpoint or documented

- **Platform fee breakdown is partial, by necessity**: the 5% cut of the listing price is shown

- **Order Detail now has real seller-view sections**: viewing your own order as its seller shows the

- **`POST /api/products` has no server-side seller-role check** (BACKEND_REFERENCE.md §3.3 — any
  authenticated user with a `universityId` can call it) — the buyer/seller split here is a client
  convention (gating the Sell entry point on `user.isSeller`), matching how the backend actually enforces

## Phase 8 status — Wallet, Referrals & Notifications

- **Screens** (`lib/features/wallet/`, `lib/features/referrals/`, `lib/features/notifications/`):
  Wallet (matches the mockup — gradient balance card, Add Money/Transactions/Withdraw/PIN quick
  actions, recent transactions), Transactions (full list), Referrals (matches the mockup — code/copy,
  native share via `share_plus`, stats, recent referrals), Notifications (matches the mockup — list,

  app bar for Profile access, `RiderHomeShell`'s Earnings tab embeds it directly (same data, "Earnings"
  is just a label swap per §3.7, not a different screen or endpoint).
- **Biometric-confirmed withdrawal (your call — implemented)**: `local_auth` prompts the device's real
  fingerprint/face unlock before submitting a withdrawal, layered client-side on top of the PIN (the
  backend only ever sees the PIN — biometrics gate whether the app sends it at all). This required two
  Android-side changes that would otherwise crash at runtime: `MainActivity` now extends
  `FlutterFragmentActivity` instead of `FlutterActivity` (local_auth's `BiometricPrompt` needs a
  `FragmentActivity`), and `minSdk` is bumped to 23 (biometric APIs need API 23+; `local_auth`'s own
  Android build already requires this).
- **Push notifications (your call — FCM built, backend gap flagged)**: `firebase_core` +
  `firebase_messaging` are wired up in `lib/core/push/push_notification_service.dart`, requesting
  permission and fetching an FCM token on app start. **This is inert until you do two things**: (1)
  create a Firebase project, register the Android app (package `com.batamart.batamart`), download
  `google-services.json` into `android/app/`, add `classpath("com.google.gms:google-services:4.4.2")`
  to `android/build.gradle.kts` and apply `id("com.google.gms.google-services")` in
  `android/app/build.gradle.kts` — none of that is done yet, since there's no real project to point at;
  (2) **a new backend endpoint** to actually store the FCM token — BACKEND_REFERENCE.md §3.10's
  `POST /api/push/subscribe` only accepts a Web Push VAPID `{endpoint, keys}` shape, which an FCM
  token doesn't fit. Until both land, `PushNotificationService.initialize()` catches the
  "Firebase not configured" error and no-ops — the app works exactly as before, just without push;
  Notifications still work fully via polling `GET /api/notifications`.
- **No bank-list or account-name-resolution endpoint exists** — the withdraw form's bank dropdown uses
  a small hardcoded list of common Nigerian banks + their standard NIBSS codes
  (`lib/features/wallet/data/nigerian_banks.dart`, public reference data), and `accountName` is typed
  manually rather than auto-verified against the account number, since BACKEND_REFERENCE.md documents
  no route for either. Expand the bank list or swap in a real lookup if Flutterwave's bank-list API
  becomes reachable from the client.
- **"Add Money" has no documented endpoint** — the mockup shows it as a quick action and even lists
  "Top up" as a transaction type, but there's no deposit/top-up route anywhere in
  BACKEND_REFERENCE.md's Wallet domain. Button is present (matching the mockup) but stubbed with a
  message explaining why, rather than silently doing nothing.
- **`WalletTransaction`'s exact shape is unconfirmed** — BACKEND_REFERENCE.md §3.7 only says
  `GET /api/wallet/transactions` returns "raw Transaction rows" without enumerating fields. Parsed
  defensively (`type`, `amount`, `description`, `createdAt`); verify field names against live data.
- **Notification deep-links to Disputes/Reports fall back to a message** (Phase 9 builds those
  screens); penalty/suspension/strike notifications currently just route home rather than to a
  dedicated account-status screen, since none exists yet either.

## Phase 9 status — Disputes & Reports

- **Screens** (`lib/features/disputes/`): Dispute: Select Order (matches WEB_PAGES_REFERENCE.md — the
  buyer's delivered/dispute-eligible orders plus already-disputed ones), File a Dispute (reason,
  description, evidence upload via the shared `UploadRepository`, pickup address), Dispute Detail
  (status, evidence, return-flow stage, buyer message thread), and a generic Report screen (used for
  reporting a rider from Order Detail — product reports already had their own flow via
  `POST /api/products/{id}/report` since Phase 4, a different endpoint from `/api/reports`).
- **Message thread is buyer-or-admin only, enforced client-side too**: BACKEND_REFERENCE.md §3.9 403s
  `GET`/`POST /api/disputes/{id}/messages` for a seller even though `GET /api/disputes/{id}` itself

  Received" action instead (seller-only despite the route's generic name, per §3.9).
